# LLM Pipeline — 전처리와 후처리

LLM 호출 하나를 실제로 성립시키는 입력·출력 처리 파이프라인에 대한 누적 정리입니다. "요청을 모델 입력으로 바꾸는 과정(전처리)"과 "모델 출력을 쓸 수 있는 결과로 바꾸는 과정(후처리)"을 다룹니다. 각 과정은 다시 애플리케이션(오케스트레이션) 레벨과 모델 내부 레벨로 나눠 봅니다.

이 주제는 원래 [agents](../agents/agents.md) 아래에 있었지만, 토큰화·샘플링·임베딩 같은 모델 내부 처리와 컨텍스트 조립·가드레일 같은 애플리케이션 처리는 에이전트뿐 아니라 챗, RAG, 배치 추론 등 모든 LLM 사용에 공통되는 기반 주제라 별도 주제로 분리했습니다. 에이전트는 이 파이프라인을 목표 달성까지 매 스텝 반복 실행하는 특수한 경우입니다.

## Current View

- 모델 성능이 서로 비슷해질수록 실제 품질 차이는 "무엇을 컨텍스트에 넣는가(전처리)"와 "출력을 얼마나 견고하게 파싱·검증하는가(후처리)"에서 갈립니다.
- 전처리·후처리는 특정 프레임워크의 기능이 아니라 LLM 애플리케이션 아키텍처의 뼈대입니다. 대부분의 실패(환각, 형식 깨짐, prompt injection, 비용 폭증)는 이 두 경계에서 발생합니다.
- 앞단(애플리케이션 레벨)은 개발자가 직접 설계·통제하는 영역이고, 뒷단(모델 내부 레벨)은 모델·서빙 스택이 담당하지만 비용·한계·품질에 직접 영향을 줍니다.

## 세부 노트

- [전처리 (Preprocessing)](preprocessing.md): 입력 수집·프롬프트 구성·컨텍스트 조립·RAG·예산 관리·가드레일(애플리케이션) + 채팅 템플릿·토큰화·임베딩·위치 인코딩(모델 내부).
- [후처리 (Postprocessing)](postprocessing.md): 로짓 가공·샘플링·디코딩·정지·디토큰화·스트리밍(모델 내부) + 파싱·구조화 검증·도구 라우팅·출력 가드레일·종료 판정(애플리케이션).

## 전체 파이프라인 한눈에

```text
요청 (사용자 입력 + 맥락)
   │
   │  [전처리 — 애플리케이션 레벨]
   ├─ 입력 수집·정규화
   ├─ 프롬프트 구성 (system · 도구 schema · few-shot)
   ├─ 컨텍스트 조립 + RAG + 메모리
   ├─ 컨텍스트 예산 관리 (truncation · 압축)
   ├─ 입력 가드레일 (injection · PII)
   └─ 직렬화 · 캐싱
        │
        │  [전처리 — 모델 내부 레벨]
        └─ 채팅 템플릿 → 토큰화 → 임베딩 → 위치 인코딩
             │
             ▼
      ┌───────────────┐
      │   LLM 추론    │
      └───────────────┘
             │
        ┌────┘  [후처리 — 모델 내부 레벨]
        └─ 로짓 가공 → 샘플링 → 디코딩 루프 → 정지 → 디토큰화 → 스트리밍
        │
        │  [후처리 — 애플리케이션 레벨]
        ├─ 파싱·추출 (tool call 분리)
        ├─ 구조화 출력 검증
        ├─ 도구 라우팅·실행
        ├─ 출력 가드레일
        └─ 포매팅 · 로깅 · 종료 판정
   │
   ▼
결과  (에이전트면: 관찰 → 다음 스텝의 전처리로 되돌아감)
```

## Open Questions

- 전처리에서 컨텍스트 예산을 truncation/요약/RAG 중 무엇으로 관리하는 것이 작업별로 유리한가?
- 후처리의 구조화 출력 보장을 constrained decoding(모델 내부)과 검증-재시도(애플리케이션) 중 어디에서 처리하는 것이 견고한가?
- 입력·출력 가드레일을 별도 모델로 둘 때와 같은 모델에 통합할 때의 비용·신뢰성 trade-off는?
