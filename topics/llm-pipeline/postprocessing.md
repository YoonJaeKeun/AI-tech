# 후처리 (Postprocessing)

후처리는 모델이 낸 raw 출력(로짓·토큰)을 사람이나 시스템이 실제로 쓸 수 있는 결과로 바꾸는 모든 단계입니다. 상위 요약은 [LLM Pipeline 허브](llm-pipeline.md)를 참고하세요.

모델 내부 레벨(로짓 → 토큰 → 텍스트)과 애플리케이션 레벨(파싱·검증·라우팅·가드레일)로 나뉩니다.

## 왜 후처리가 필요한가

모델의 raw 출력은 "토큰 확률로 만들어진 텍스트"일 뿐이라, 그대로는 시스템이 신뢰하고 쓸 수 없습니다. 후처리가 없으면 다음이 깨집니다.

- **형식이 보장되지 않는다**: 확률적 생성이라 JSON을 요청해도 깨진 JSON, 여분의 설명, 코드펜스가 섞여 나올 수 있습니다. 파싱·검증 없이는 다운스트림이 바로 실패합니다.
- **텍스트는 그 자체로 행동이 아니다**: tool call도 결국 텍스트로 나올 뿐이라, 추출·검증·디스패치하지 않으면 아무 일도 일어나지 않습니다. 후처리가 "말"을 "실행"으로 바꿉니다.
- **환각이 걸러지지 않는다**: 모델은 그럴듯하지만 틀린 내용을 확신 있게 냅니다. grounding 검증(근거 대조) 없이는 그대로 사용자에게 전달됩니다.
- **안전·규정 리스크가 노출된다**: 유해 콘텐츠, PII/PHI 유출, 정책 위반이 사용자·시스템에 닿기 전 마지막 방어선이 출력 가드레일입니다. 임상·금융처럼 규제가 있는 도메인에서는 특히 필수입니다.
- **출력이 비결정적이다**: 샘플링 때문에 같은 입력도 매번 달라집니다. 검증·재시도로 일관성을 확보하지 않으면 "가끔 되고 가끔 깨지는" 시스템이 됩니다.
- **경계가 불명확하다**: 출력이 어디서 끝났는지, reasoning과 최종 답이 어디서 갈리는지 파싱하지 않으면 잘림·과생성·혼합이 발생합니다.

### 예시: 같은 출력, 후처리 유무 차이

도구 호출을 기대한 상황에서 모델이 이렇게 냈다고 합시다.

> 음, 날씨를 확인해야겠네요.
> `{"tool": "get_weather", "city": "Seoul"}`
> 바로 확인해볼게요!

- **후처리 없이**: 이 전체 문자열을 도구 실행기에 그대로 넘기면 JSON 파싱이 실패하고, 설명 문장까지 섞여 있어 실행할 수 없습니다 → 에러.
- **후처리 있이**: (1) 파싱으로 JSON 부분만 추출 → (2) 스키마 검증으로 `tool`·`city` 필드 확인 → (3) 라우팅으로 `get_weather(city="Seoul")` 실행 → (4) 검증 실패 시 repair prompt로 재요청. 같은 출력이 비로소 "실행 가능한 행동"이 됩니다.

## 후처리가 주는 것 (유용한 점)

- **신뢰성**: 구조화 출력 검증 + 실패 시 재시도가 "가끔 되는 것"을 "항상 되는 것"으로 만듭니다. 프로덕션 시스템의 전제 조건입니다.
- **시스템 통합**: 파싱·스키마 검증으로 확률적 LLM 출력을 결정적 시스템(API, DB, UI)에 안전하게 연결합니다.
- **에이전트 자율성**: tool call 추출 → 실행 → 결과 반환이 에이전트 루프를 돌립니다. 후처리가 없으면 에이전트 자체가 성립하지 않습니다.
- **안전성 보장**: 출력 가드레일이 브랜드·법적·윤리 리스크를 사용자에게 닿기 전에 차단합니다.
- **관측성과 개선 루프**: 평가·로깅으로 실패를 측정하고, 그 신호를 프롬프트·전처리로 되먹여 개선합니다.
- **비용·지연 최적화**: 스트리밍으로 체감 지연을 줄이고, 조기 정지로 토큰을 아끼며, 검증 실패를 일찍 감지해 낭비를 줄입니다.
- **사용자 경험과 검증 가능성**: 포매팅·인용·근거 표시로 사람이 결과를 신뢰하고 직접 검증할 수 있는 형태로 다듬습니다.

## 모델 내부 레벨

### 1. 로짓 산출 (Logits)

- 마지막 레이어가 다음 토큰 후보 전체(vocabulary 크기)에 대한 점수(logits)를 냅니다. 아직 확률도, 텍스트도 아닙니다.

### 2. 로짓 가공 (Logit processing)

- temperature scaling: 값이 높을수록 분포가 평탄해져 다양성이 커지고, 낮을수록 뾰족해져 결정적이 됩니다.
- repetition / frequency / presence penalty, `logit_bias`, bad-words 마스킹으로 특정 토큰을 억제·촉진합니다.
- top-k / top-p(nucleus) 필터로 후보를 축소합니다.
- 제약 디코딩(constrained / grammar decoding): JSON schema나 정규문법을 강제해 출력 형식이 항상 유효하도록 만듭니다.

### 3. 샘플링 (Sampling)

- greedy(항상 최고 확률) / temperature / top-p / top-k / beam search 중 선택합니다.
- 결정성: seed 고정 여부. temperature=0이라도 하드웨어·병렬 처리 때문에 완전히 결정적이지 않을 수 있습니다.

### 4. 자기회귀 디코딩 루프 (Autoregressive decoding)

- 토큰 하나 생성 → KV cache 갱신 → 다시 다음 토큰을 생성합니다. 출력 길이만큼 이 과정을 반복합니다.
- speculative decoding 등으로 이 루프를 가속합니다.

### 5. 정지 조건 (Stopping)

- EOS token, 사용자가 지정한 stop sequence, `max_tokens`, 시간 초과에서 멈춥니다.
- 정지 처리 실수는 답이 잘리거나(under-generation) 불필요하게 길어지는(over-generation) 문제로 이어집니다.

### 6. 디토큰화 (Detokenization)

- 토큰 ID를 다시 텍스트로 되돌립니다. special token 제거, subword 병합, 공백·대소문자 복원이 포함됩니다.

### 7. 스트리밍 (Streaming)

- 생성되는 델타 토큰을 즉시 전송합니다(SSE 등). 부분 출력에 대한 점진적 파싱이 필요해집니다.

## 애플리케이션 / 오케스트레이션 레벨

### 1. 파싱과 추출 (Parsing & extraction)

- reasoning/thinking 블록과 최종 답을 분리하고, tool call(함수명 + 인자)을 추출하며, 코드블록·마크다운 구조를 파싱합니다.
- 스트리밍 중이면 부분 파싱과 "언제 완결되었는지" 판단이 함께 필요합니다.

### 2. 구조화 출력 검증 (Structured output validation)

- JSON schema·타입 검증, 필수 필드 확인을 합니다.
- 어긋나면 재시도(repair prompt로 다시 요청)하거나, 애초에 모델 내부의 constrained decoding으로 폴백합니다.

### 3. 도구 라우팅과 실행 (Tool routing & dispatch)

- 추출한 호출을 실제 함수에 매핑하고, 인자 검증·권한 확인 후 실행하며, 결과를 정규화합니다.
- 실패는 숨기지 말고 관찰로 되돌려 모델이 스스로 재시도·수정하게 하는 것이 견고합니다.

### 4. 출력 가드레일 (Output guardrails)

- 유해성·안전성 필터, PII/PHI 유출 검사, grounding 검증(주장 vs 근거 대조로 환각 탐지), 정책·컴플라이언스 확인.

### 5. 후정렬과 포매팅 (Post-formatting)

- 사용자용 렌더링, 인용·각주 삽입, 단위·표기 정리, 민감정보 마스킹.

### 6. 평가와 로깅 (Eval & logging)

- 트레이싱, 토큰·비용 집계, 자동 품질 스코어링(LLM-as-judge 등), 사용자 피드백 수집으로 개선 루프를 만듭니다.

### 7. 종료 판정 (Termination — 에이전트 맥락)

- 도구 호출이 있으면 실행 후 그 결과를 다음 스텝의 전처리로 되돌리고, 없으면 최종 답으로 종료합니다. 이 판정이 [agent loop](../agents/agent-loop.md)를 돌립니다.

## 후처리는 어디서 일어나는가 (외부화 가능성)

후처리 대부분은 모델 바깥에서 이뤄지고, 그렇게 하는 것이 표준입니다. 다만 "외부"를 두 가지로 나눠야 정확합니다.

- **가중치(모델) 외부**: 파인튜닝 없이 모델은 그대로 두고 출력만 처리. 거의 모든 후처리가 여기 해당합니다.
- **추론 프로세스 외부**: 모델을 완전한 블랙박스로 두고 최종 출력만 받아 처리. 이 지점에서 단계별로 갈립니다.

이 구분은 위의 **애플리케이션 레벨 vs 모델 내부 레벨** 구분과 그대로 겹칩니다.

- **애플리케이션 레벨(파싱·검증·라우팅·가드레일·포매팅·로깅·종료)은 전부 완전 외부입니다.** 선택이 아니라 표준 아키텍처입니다. 호스티드 API는 모두 블랙박스이고, 반환된 텍스트·tool_calls를 개발자 코드에서 처리합니다. 에이전트 루프가 블랙박스 API만으로 도는 이유가 이것입니다.
- **모델 내부 레벨(로짓 가공·샘플링·디코딩·디토큰화)은 접근 권한에 따라 다릅니다.**

| 접근 방식 | 로짓·샘플링 단계의 외부 처리 |
| --- | --- |
| 호스티드 API(블랙박스) | 직접 불가. `temperature`·`top_p`·`stop`·`response_format`·`logit_bias` 같은 파라미터로 지시만 하고 계산은 서버 안에서. logprobs를 노출하면 외부 신뢰도 추정·재랭킹 정도는 가능. |
| self-host / 오픈 웨이트(vLLM·TGI·llama.cpp) | 가능. 디코드 루프에 커스텀 logit processor나 문법 강제(constrained decoding)를 훅으로 삽입. 가중치는 그대로라 "가중치 외부, 디코드 루프 내부". |

### 예: "항상 유효한 JSON"을 얻는 세 위치

1. **완전 외부(어떤 API든)**: 호출 → 검증 → 실패 시 repair prompt로 재호출. 모델 무관하지만 100% 보장은 아니고 재시도 비용이 듭니다.
2. **프로바이더 기능**: `response_format`/structured output. 서버가 constrained decoding을 대신 처리하고, 나는 요청만 합니다.
3. **self-host constrained decoding**(Outlines·guidance·GBNF 문법): 디코드 루프에서 직접 강제. 보장되고 가중치는 무변경.

### 완전 외부 후처리의 대표 패턴

출력 안전성 검사는 두 번째 모델을 바깥에 세워 첫 모델의 출력을 검사하게 하는 방식이 흔합니다(moderation 분류기, Llama Guard 등). 메인 모델과 독립적으로 교체할 수 있는 전형적인 "모델 밖 후처리"입니다.

정리하면, 오케스트레이션 절반은 원칙적으로 전부 외부화가 가능하며 그렇게 하는 것이 바람직합니다(모델 교체 가능, 테스트·통제 용이). 블랙박스 API로 외부화가 안 되는 유일한 부분은 로짓·샘플링 수준의 제어이고, 이는 프로바이더 파라미터를 쓰거나 self-host로 디코드 루프를 잡아야 합니다.
