### Exploring File Uploads and Downloads in MCP — 파일 바이트를 모델 컨텍스트 밖에서 주고받는 실험적 확장안(`io.modelcontextprotocol/files`) 공개

- source_url: https://blog.modelcontextprotocol.io/posts/exploring-file-uploads-and-downloads-in-mcp/
- published: 2026-11-10
- type: proposal
- topics: agents
- status: read
- confidence: high

#### Why It Matters

- 확장 창(지난 7일) 포함 자료입니다. 발행일(11-10)은 24시간 기본 창에도 들어오지만, 바로 위 릴리스 주기 발표와 같은 블로그에서 연속해서 나온 자료라 함께 묶어 기록합니다.
- Adopt의 "LLM 전처리·후처리 경계를 명시적으로 설계하기" 판단과 직접 맞닿습니다. 큰 파일을 모델 컨텍스트에 base64로 밀어넣지 않고 클라이언트-서버-제3자 스토리지 사이에서 직접 주고받게 하는 설계로, "컨텍스트에 무엇을 넣는가"의 경계를 프로토콜 레벨에서 명시합니다.
- credentials `omit`/`include` 구분, 리다이렉트 거부, 다운로드 파일을 다이제스트가 맞아도 신뢰하지 말라는 명시는 topics/safety-governance.md Risk Areas의 "Prompt injection and tool hijacking", "Data leakage"와 같은 축의 구체적 설계 대응입니다.

#### Key Points

- 확장 식별자 `io.modelcontextprotocol/files`, 프로토콜 리비전 2026-07-28 이상 대상. File Uploads Working Group이 개발 중이며, 참조 구현은 아직 없고 연내 확정을 목표로 합니다.
- 업로드: 서버가 도구 입력 스키마에 `x-mcp-file`로 파일 인자를 표시(허용 MIME, 최대 크기 지정 가능). 작은 파일은 `maxInlineBytes` 한도 내에서 base64 인라인, 큰 파일은 별도 업로드. 클라이언트가 먼저 메타데이터만으로 도구를 호출해 서버가 권한·쿼터를 먼저 검사하고, 호스트도 사용자 승인을 먼저 받습니다. 검사를 통과하면 서버가 `upload_required` 결과(업로드 대상 URL, 변조 방지된 `requestState`)를 반환하고, 업로드 후 같은 인자+`requestState`로 재호출합니다. 일부 도구는 `requestState`를 1회용으로 제한해 중복 실행을 막습니다.
- 다운로드: 도구 결과의 `_meta` 필드에 다운로드 대상을 담아 모델용 일반 `content`와 함께 반환. 클라이언트가 HTTPS GET으로 받고 `size`와 (있다면) SHA-256 `digest`를 검증합니다. 다이제스트가 맞아도 파일이 안전하다는 뜻은 아니므로 다운로드 파일은 계속 비신뢰로 취급해야 한다고 명시합니다.
- 보안: 각 대상의 `credentials`가 `omit`(MCP 자격증명 미전송, 사전서명 URL 등 자체 인가 사용) 또는 `include`(MCP 서버 자신의 origin에만 자격증명 전송)로 구분됩니다. 클라이언트는 리다이렉트를 거부하고, 자체 `Authorization` 헤더를 제공하는 대상도 거부해야 합니다. `omit` 대상을 origin allowlist로 제한하라고 권고하지만 의무화 여부는 열린 질문입니다.
- 역량 협상: 서버는 `server/discover`에서 `upload`·`maxInlineBytes`를 알리고, 클라이언트는 `io.modelcontextprotocol/clientCapabilities`에서 `upload`/`download` 지원을 선언합니다.
- 저자: Den Delimarsky(Lead Maintainer), Wil St. Charles(Google).

#### Limitations

- 아직 실험적 제안 단계로, 참조 구현이나 SEP 번호가 이 글에서 확인되지 않았습니다. 다운로드 대상을 `_meta`에 둘지, origin allowlist를 의무화할지는 저자들도 열린 질문으로 남겼습니다. 확정 스펙이 아니므로 이번 실행에서는 변경 가능성을 전제로 기록합니다.

#### My Take

- 기존 판단과 같은 방향입니다. 다만 아직 확정 스펙이 아니라는 점은 분명히 남겨, 다음에 이 주제를 다룰 때 "확정됐는지"부터 확인해야 합니다.

#### Limitations

- justice.gov(SDNY 보도자료)가 이번 실행에서 egress 차단으로 열리지 않았습니다. `source_url`은 WebSearch로 `site:justice.gov`를 검색해 실제로 확인한 canonical 주소(`justice.gov/usao-sdny/pr/three-foreign-nationals-arrested-and-charged-scheme-use-super-intelligence-defraud`)이며, 지어낸 URL이 아닙니다.
- Gizmodo, SCMP, ITV, SecurityWeek, ynetnews, jns 등 서로 독립된 비애그리게이터 출처 여럿이 피고인 이름·혐의·1억 2,900만 달러 규모를 동일하게 보도해 교차 확인했습니다.
- 발표(기소 공개) 날짜는 출처마다 2026-11-05와 2026-11-06으로 어긋나 `published`를 `unknown`으로 적었습니다. 범행 기간(2024-07~2026-02 vs "2024~2026")도 출처마다 달라 기록하지 않았습니다.
- 원문을 못 열어 혐의 내용이 기소장 그대로인지, 또는 "Super Intelligence Task Force" 같은 일부 저품질 출처의 표현이 실제 기소장 용어인지 확인하지 못했습니다.
